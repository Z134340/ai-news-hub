# SKILL — 技術棧層間移動的模式與反例

適用於判 `trajectory`。上位規則:`ROADMAP_RUBRIC.md` RM-3。S1–S6 的**定義**在 `Hermes-Agent/curator/TECH_RUBRIC.md`,本檔只談它們之間**怎麼移動**。

## 一句話

技術主題不是在原地變強或變弱,而是**在棧的層與層之間移動**。看懂移動方向,比看懂當下熱度更能推下一步。

工程機械類比:一個零件的成熟過程是「實驗室加工 → 標準件 → 目錄品項」。它不是變得更精密,是**移到供應鏈的下一格**。技術棧的移動是同一回事。

## 六條典型路徑

| 路徑 | 白話 | 對應 `trajectory` |
|---|---|---|
| S2 → S4 | 模型本身穩定後,價值移到怎麼編排它 | `layer_shift` |
| S4 → S6 | 編排框架收斂,焦點變成誰真的導入了 | `layer_shift` 或 `commoditizing` |
| S1 → S6 | 算力層的改良直接反映成應用層的可負擔性 | `commoditizing` |
| S3 → S5 | 資料與知識的爭議轉成資料權與監理 | `consolidating` |
| S2 → S1 | 模型架構的改良回頭吃算力(反向,較少見) | `capability_deepening` |
| S5 獨立驅動 | 監理不跟隨技術節奏,自己有議程 | `consolidating` |

**S5 是唯一不跟隨技術成熟度的層。** 監理與立法有自己的時程表(法案排程、諮詢期、生效日),不會因為技術更成熟就加速。看到 S5 佔比升高,不要推論「技術更成熟了」,要推論「制度面在動」。

## 怎麼判「真的在移動」

判 `layer_shift` 需要三個條件同時成立:

1. `secondary_layers` 裡有那個目標層(**不是你自己讀標題讀出來的**——自己判層違反 §2 權限邊界)
2. T3 增量幅度 ≥ D2(層移是結構性變化,D0/D1 的漸進改良不會造成層移)
3. `stage` 不是 `plateau`/`declining`(RM-1:原地打轉時沒有層移的新訊號)

三缺一 → 判 `capability_deepening` 或其他,不判 `layer_shift`。

## 四個反例

| 情況 | 看起來像 | 實際是 |
|---|---|---|
| 第二層只出現一次 | 層移的開端 | **雜訊**。單次出現是隨機的,不是趨勢 |
| S6 佔比升高 | 技術在普及 | 可能是 **fallback**。S6 在 TECH_RUBRIC 是預設落點(實測 fallback 佔 8.3%),分不出層的都掉進去 |
| S5 佔比升高 | 這個技術有安全問題 | S5 同時涵蓋技術性安全與**制度面**。是紅隊研究還是監理草案,兩者的前瞻含義完全相反 |
| 兩層佔比接近 | 正在移動的中間狀態 | 也可能是**主題本身跨層**(如「AI 治理」天生同時在 S4 與 S5)。跨層主題不會移動,它一直在那裡 |

第二列與第四列是最容易誤判的兩個。判 `layer_shift` 之前先問:這是層在移,還是分類器把分不出來的都丟到同一格?

## 判不出來的時候

層別訊號不清楚,不要為了填欄位而挑一個「看起來合理」的 `trajectory`。可用的保守選項有兩個:

- 有明確的「沒進展」訊號(T3 ≤ D1 且 `stage` 是 `plateau`/`declining`)→ `stalling`
- 什麼都判不出來 → `unforecastable`

`stalling` 和 `unforecastable` 的差別:前者是「我判斷它沒在動」(一個判讀),後者是「我判斷不了」(拒絕判讀)。**不要用 `stalling` 當萬用垃圾桶**——那會讓 dashboard 上出現一堆假的「停滯」標籤,而實際上只是資料不夠。
